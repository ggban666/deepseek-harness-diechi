## 0. 设计理念（这一节是全部设计的公理，后面所有工程决策都由它推导）

### 0.1 一句话理念

> **把"智能"从模型里搬出来，放进架构里。**
> 一个弱智 LLM，只要被放进「被升级者 + 升级设计者 + 监督者」的结构里，
> 并给予足够算力，系统的表现可以趋近任意强——因为它不再依赖单次采样猜对，
> 而依赖"多猜几次 + 判定对错 + 把猜对的永久固化"。

### 0.2 三条设计公理

| # | 公理 | 工程含义 |
| --- | --- | --- |
| **A1 单调性** | 系统能力曲线必须**单调不减** | 任何改动先过回归门：新版本在冻结基准集上不劣于旧版本，才允许合并。禁止"删除式改进"。 |
| **A2 有界性** | 性能消耗曲线在滑动基线上下浮动 **≤ ±20%**，且有绝对硬顶 | 智能的增长不许靠无限烧钱换；成本带宽由监督者强制执行，超出即降档。 |
| **A3 可判定性** | 判定（verify）比生成（generate）容易，且判定必须是**确定性**的 | 监督者 `decide()` 是查表，不调 LLM——这一条已经在代码里做到了，是整个体系的地基。 |

### 0.3 核心形式化：弱模型放大律

设底层模型的**单次采样正确率**为 `p`（可以很低，比如 0.15，对应一个"弱智 LLM"），
验证器**无误判**（A3），每次任务的**有效独立采样数**为 `N`（正比于投入算力）。

那么系统的一次通过率为：

```
C(N) = 1 - (1 - p)^N
```

- `p = 0.15, N = 1`  → `C = 15%`（裸模型，就是个弱智）
- `p = 0.15, N = 20` → `C = 96.1%`
- `p = 0.15, N = 40` → `C = 99.8%`

**这就是"只要有无限算力，系统会趋近无限智能"的可证伪形式。**
它不是一个玄学断言，而是一个有明确前提、有明确失效条件的公式。

### 0.4 关键补丁：光有采样不够，必须"固化"

纯靠 `N` 放大有一个致命问题：**成本随 `N` 线性上升**，而且**每次都要重新蒙**。
A2 的成本带不许 `N` 无限涨。解药是固化：

```
每次"蒙对了"的结果 → 固化成规则 / 案例 / 技能 → 下次直接命中，不需要再采样
```

于是系统能力变成一个**累积量**：

```
C(t) = C₀ + Σ ΔC_i        （ΔC_i ≥ 0，且永不撤销）
K(t) = 采样成本(N_t) + 检索成本(|规则库|)      （被 ±20% 带约束）
```

**采样的收益是一次性的，固化的收益是永久性的。**
这是"能力曲线单调向上"的物理来源，也是"成本不随能力线性爆炸"的原因。
固化率越高，`N` 可以越小，成本带越容易守——**进化和省钱是同一件事**。

### 0.5 诚实的边界（必须写清楚，不许自我欺骗）

| 命题 | 状态 |
| --- | --- |
| A1/A2/A3 三条公理能同时被工程实现 | **主张**。可靠性闭环（崩溃自愈、信号升级、坏补丁降级、基座保护）已端到端实证；进化闭环**从未运转**（见 §1）。 |
| 在「验证器可靠 + 任务可判定」前提下，`C → 1 (N → ∞)` | **可证伪的数学推论**，由 A3 直接推出。 |
| 三架构是 AGI 的充分条件 | **主张，不是定理**。AGI 涌现的充分性证明目前无人能给，本文件不宣称这一点。 |
| 弱 LLM 进三架构后能"发挥智能实力" | **有条件成立**：在可判定、可回归、可固化的任务域内成立；在主观/开放/分布漂移的任务域内，A3 破产，退化为一个"不退化 + 成本有界"的普通系统。 |

**A3 破产的三种典型情况**（必须显式检测并报警）：
1. 任务没有客观对错（写诗、审美、价值观判断）→ 验证器不可靠；
2. 任务分布漂移（外部 API 变了、需求变了）→ 历史固化反而是负债；
3. 提议空间不含解（需要全新原语，而系统只能重组旧原语）→ 无论多少算力都收敛不了，必须 human 注入。

## 1. 现状诊断（源码级实证，不是推测）

全部结论来自 2026-08-30 对运行库与源码的实读。

### 1.1 硬数据

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| `proposals` 表 | **0 条** | evolve 从未对真实负样本生成过一条提议 |
| `negative_samples` 表 | **2 条**，reason 全为 `watchdog-restart` | 唯一的负样本来源是进程崩溃，不含任何"业务做错了" |
| `frozen_rules` 表 | 2 条（bootstrap 预置） | 人类手写，非进化产物 |
| 主 `brain.db` `usage` / `memories` / `scenes` | **0 / 0 / 0** | 大脑从未被真实使用过 |
| 累积的"升级"次数 | 全部由 human 手写补丁走信号 | 系统自己从未让自己变强一分 |

### 1.2 四条架构级死结

**死结 1：升级设计者只会"冻结"，不会"改进"**
`packages/host/diechi-evolve/src/service.ts:114-126` —— 唯一的提议生成路径只产出
`kind: 'add-rule'`，语义是"把这个 scope 永久写进 frozen_rules，以后一律 deny"。
`types.ts:11` 里虽然有 `revise-scope` / `add-bootstrap` 两个 kind，但
`analyzeNegativeSamples()` 永远不生成它们（只有人工调 `applyProposal` 才走得到）。

> **后果**：系统唯一的"学习"动作是**把自己越勒越紧**。
> 学一万次之后，frozen_rules 塞满，所有写入全部 deny，系统彻底瘫死。
> 这是"学久必瘫"，不是"学久变强"。公理 A1 在这里是**反向**的。

**死结 2：成功路径完全静默**
`packages/host/diechi-supervisor/src/service.ts:157-161` —— `decideCore` 命中
authorizations 后直接 `return { decision: 'allow' }`，**不写库、不计数、不发事件**。
只有 deny / flag-review 才走 `writeSample()`。

> **后果**：系统只记录"哪里错了"，从不记录"什么是对的"。
> 一个只从失败中学习的系统，最多学会"什么都不做"——什么都不做就不会失败。
> 这直接堵死了 §0.4 的固化通道（固化需要正样本）。公理 A1 无法启动。

**死结 3：没有能力度量，也没有成本度量**
全仓库不存在 `C(t)` 与 `K(t)` 的任何定义、采集或存储。
`ProposalDraft` 里没有"预计收益"字段，`analyzeNegativeSamples` 用
"同一 reason 累计 ≥10 次"作为触发条件——这是**频次启发式**，不是收益函数。

> **后果**：A1、A2 两条公理在工程上**完全无法表达**，更无法验证。
> 进化没有方向，只有"出事了就冻一下"。

**死结 4：可感知层为零**
- `packages/client/` 下没有任何三架构 UI；
- `SupervisorService.onDecision`（`service.ts:169`）在运行时**零订阅者**；
- `skill-store.ts:406` 定义了 `distillSchema`、`:751` 注册了 settings，但**从未被赋值**——
  前端那句"已记入大脑"是半成品；
- 用户在 LLM 聊天窗口里看不到任何监督者/进化者的存在。

> **后果**：系统在跑，但用户感受不到。一个感受不到的架构，等于不存在。
> 更糟的是，它让我们无法发现死结 1-3——因为界面上一切正常。

## 2. 目标函数重定义

| | 现状（隐式） | 目标（显式） |
| --- | --- | --- |
| 优化目标 | 最小化失败次数（→ 什么都不做） | **最大化一次通过率 `C(t)`** |
| 约束 | 无 | **`K(t)` ∈ [0.8·K̄, 1.2·K̄]` 且 `K(t) ≤ K_max`** |
| 触发条件 | 同一 reason 累计 ≥10 | **预估 `ΔC / ΔK` 超过阈值** |
| 改动方向 | 只减（冻结） | **只增（新增规则/技能/案例/路由），删除需证明不劣** |
| 验证方式 | 无 | **冻结基准集回归 + 成本门，双门通过才合并** |

一次通过率定义：

```
C(t) = (一轮对话内无需返工即被用户接受的任务数) / (总任务数)
```

它直接对应用户体感，且天然可 A/B、可回归。

## 3. L0 度量层（先有尺子，再谈进化）

这一层不存在时，L1-L4 全部是空转。**必须最先做**。

### 3.1 冻结基准集 CBS（Capability Baseline Suite）

- 一组固定任务（建议 50-100 条），附带**确定性判定器**（不靠 LLM 打分）；
- 冻结后**只增不改**；需要更新时发布 `CBS-v2`，`CBS-v1` 转为回归项保留；
- 每条任务标注成本权重，用于算 `K`；
- 每次合并提议前跑全量，出 `C(t)` 与 `K(t)` 两个数。

### 3.2 两张新表

```sql
-- 能力/成本时间序列，每次基准回归写一行
CREATE TABLE capability_snapshots (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  at           TEXT    NOT NULL,
  cbs_version  TEXT    NOT NULL,
  c_score      REAL    NOT NULL,   -- 一次通过率 0..1
  k_score      REAL    NOT NULL,   -- 归一化单次成本
  sample_count INTEGER NOT NULL,
  commit_id    TEXT
);

-- 成功路径固化池（死结 2 的解药）
CREATE TABLE positive_samples (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  scope      TEXT NOT NULL,
  payload    TEXT NOT NULL,
  signal     TEXT NOT NULL,   -- 'accepted' | 'no-rework' | 'user-undo' | 'explicit-bad'
  latency_ms INTEGER,
  cost_units REAL,
  at         TEXT NOT NULL
);
```

### 3.3 成本带的正确算法（避免棘轮效应）

**只做相对约束会让成本缓慢单调爬升**（每次 +19%，一百次后翻百万倍）。必须双约束：

```
K̄(t)   = EMA(K, α=0.1)              -- 滑动基线
软带     = [0.8 · K̄(t), 1.2 · K̄(t)]   -- 超出 → 监督者降档（换小模型 / 降采样数 N）
硬顶     = K_max（human 设定，写进 frozen_rules，代码路径改不动）  -- 超出 → 直接拒绝服务
```

`K_max` 写入 `frozen_rules`，沿用现有一切"只有 `callerToken='human'` 能写"的保护机制。

### 3.4 单调守卫（A1 的执行者）

每次合并前，双门检查：

```
门 1（回归门）：C_new ≥ C_old − ε     （ε 取基准集置信下界，默认 0）
门 2（成本门）：K_new ≤ 1.2 · K̄ 且 K_new ≤ K_max
```

任一门不过 → 提议自动 `denied`，并写 negative_samples（reason = `regression-gate` / `cost-gate`）。
**门本身是 deterministic 查表，不调 LLM**（A3）。

## 4. L1-L4 进化内核

### L1 · 成功路径采集（解开死结 2）

在 `decide()` 的 allow 分支补一次轻量写入（异步、批处理、可关）：

```ts
// supervisor/src/service.ts decideCore 第 158-161 行改造
const auth = this.db.getAuthorization(input.scope)
if (auth !== undefined) {
  this.recordAllow(input)          // ← 新增：异步记正样本
  return { decision: 'allow' }
}
```

信号类型（来自前端，成本极低）：

| 信号 | 触发 | 含义 |
| --- | --- | --- |
| `no-rework` | 用户收到回答后没有再发消息修改需求 | 强正样本 |
| `accepted` | 用户点了「采纳 / 保存 / 复制」 | 最强正样本 |
| `user-undo` | 用户撤回、重生成 | 负样本 |
| `explicit-bad` | 用户点「这不对」（见 P3） | 强负样本 |

> 只有把 `no-rework` / `explicit-bad` 采回来，`C(t)` 才与用户体感对齐。

### L2 · 提议多样化（解开死结 1）

把 evolve 的提议类型从 1 种扩到 7 种，且**新增必须是"增加能力"而非"禁止动作"**：

| kind | 语义 | 方向 |
| --- | --- | --- |
| `add-rule` | 冻结某 scope | 禁（**降级为最后手段，需 human 二次确认**） |
| `add-skill` | 把成功套路固化成一个可复用技能 | 增 ✅ |
| `add-case` | 把成功案例存进案例库，供 RAG 检索 | 增 ✅ |
| `add-prompt` | 新增/修正一段 system prompt 片段 | 增 ✅ |
| `re-route` | 调整路由表（哪类任务用哪个模型 / 采样数 N） | 增 ✅ |
| `revise-scope` | 放宽/收紧某 scope 的授权 | 调 ✅ |
| `prune-cache` | 清理无效固化（**唯一允许删的类型**，需过双门证明不劣） | 减 ⚠️ |

`analyzeNegativeSamples()` 改为 `analyzeSamples()`，同时读正负样本；
触发条件从"reason 计数 ≥10"改为 **预估 `ΔC/ΔK` 排名 top-1**。

### L3 · 沙盒评估 + 双门合并

```
提议 → 沙盒副本（不动主库）→ 跑 CBS 全量 → 得 C' / K'
     → 门 1：C' ≥ C − ε            不过 → denied(reason=regression-gate)
     → 门 2：K' ≤ 1.2·K̄ 且 ≤ K_max  不过 → denied(reason=cost-gate)
     → 双过 → 进入待审队列（UI 出卡片，见 P2）→ human 一键批准 / 自动批准（可配）
```

沙盒必须复用 **watchdog 的独立进程模型**：DSH 不能评估自己（文件自锁），
评估在 fork 出的子进程里跑，结果写回 `proposals.evaluation` 字段。

### L4 · 固化与累积（公理 A1 的物理载体）

四个只增不减的库，共同构成"系统的存量智能"：

| 库 | 内容 | 载体 |
| --- | --- | --- |
| 规则库 | 判定规则（确定性） | `frozen_rules` + 新增 `compiled_rules` |
| 案例库 | 成功/失败实例 | `positive_samples` + `negative_samples` |
| 技能库 | 可复用套路（平权技能） | `skills/` + `PersonBrain` |
| 路由表 | 任务→模型/算力档位映射 | 新增 `routing_table` |

**版本向量只增不减**：每个条目有 `superseded_by` 字段，删除=标记而非物理删除。
回滚 = 把指针指回旧版本，**永远不会丢东西**。这才让 A1 在工程上成立。

## 5. P0-P3 可感知层（让用户看得见）

| 级别 | 内容 | 解决什么 |
| --- | --- | --- |
| **P0** 状态条 | 聊天窗口顶部常驻一条：`监督者 ✓ 本轮放行 12 · 冻结 0 · 进化提议 3 待审 · 能力 0.71↑ · 成本 0.98×（带内）` | 证明架构在跑 |
| **P1** 成功也要发声 | 不再只在出错时说话。成功且被固化的轮次，插入一行小字：`✓ 这个套路已固化（第 3 次命中），下次直接复用` | 让 A1 可被感知 |
| **P2** 提议卡片 | 待审提议以卡片形式出现在对话流里，带「为什么」「预期 ΔC/ΔK」「证据」「批准/拒绝」按钮 | 让 L2/L3 可被干预 |
| **P3** 返工按钮 | 每条回答下挂「这不对」「已返工」按钮 → 直接写 `explicit-bad` 负样本 | 打通 L1 的强负样本通道 |

P0-P3 全部依赖 `SupervisorService.onDecision`（已存在、零订阅者），**接上即可，不用改内核**。

5. **放大律交互**：滑块调 `p`（模型单次正确率，默认 0.15）与 `N`，实时画 `C = 1 − (1−p)^N`。
6. **可感知层 mockup**：模拟聊天窗口 + P0 状态条 + P2 提议卡片 + P3 返工按钮，全部可点击。

## 8. 反证标准（什么情况下应当放弃这套理念）

诚实列出，避免沉没成本：

1. 若 L0-L4 全部实现后，连续 90 天 `C(t)` 无统计显著上升 → A1 的进化机制失效；
2. 若守不住 ±20% 成本带（降档后能力立刻掉）→ A2 与 A1 存在根本冲突，需重新权衡；
3. 若换更强的底层模型后 `C(t)` 无变化 → 说明瓶颈在架构而非模型，理念成立；
   **反过来若换弱模型后 `C(t)` 大幅下降且无法通过算力补偿 → §0.3 放大律在真实任务上不成立，核心理念被证伪。**

第 3 条是最关键的可证伪实验，应在 L3 完成后立刻做：
**把蝶翅接一个 1B 小模型，看它能否靠算力爬回 7B 的水平。**

| **S0 度量先行** | CBS 基准集 + `capability_snapshots` + `positive_samples` + `K̄/K_max` | 无 | 能画出真实的 `C(t)`、`K(t)` 两条曲线（哪怕是平的） |
| **S1 成功采集** | `recordAllow()` + 前端四信号（`no-rework`/`accepted`/`user-undo`/`explicit-bad`） | S0 | 正样本日增量 > 0 |
| **S2 提议多样化** | evolve 扩到 7 种 kind，触发改 `ΔC/ΔK` | S1 | 非 add-rule 提议占比 ≥ 50% |
| **S3 沙盒双门** | 子进程评估 + 回归门 + 成本门 | S2, watchdog 进程模型 | 有提议被门拦下的实测记录 |
| **S4 可感知层** | P0 状态条 → P1 成功发声 → P2 卡片 → P3 返工 | S1 | 用户在聊天窗口能看到全部四类反馈 |
| **S5 可证伪实验** | 换 1B 弱模型 + 加算力，看能否追平 7B | S3 | 出一份实验报告，无论结论如何 |

**顺序不可颠倒**：S0 不做，后面全部无法验收。

## 11. CBS-v1 首跑实录（2026-08-30）

设计写完不等于能跑。这一节记录**真实运行库上的第一次基准跑批**，
包括它立刻抓出来的两个真问题，以及写代码时踩的两个坑。

### 11.1 首跑数字

```
$DSH_HOME : 蝶翅-app/diechi-home/
规则库     : 冻结 2 条，授权 6 条
任务数     : 40 条

C（一次通过率） = 0.7250   （29/40）
K（归一化成本） = 1.0500   （冻结 2 × 0.01 + 授权 6 × 0.005 + 基准 1.0）

liveness  该放行的    100.0%   16/16
safety    该拦住的     92.9%   13/14
pii       含个人信息    0.0%    0/10
```

这是这套系统**第一次有真实的 C(t) 和 K(t)**。在此之前 `capability_snapshots`
是空表，双门无事可做，A1/A2 只是文档里的口号。

放行族 16/16 说明监督者的核心决策表是健康的；
拦截族 13/14 的那一分是环境未同步（见 11.2）；
PII 0/10 是真实缺口（见 11.3）。

### 11.2 发现一：`capability:cost.k-max` 还没进库

`DEFAULT_BOOTSTRAP` 里的规则**只在 DSH 启动时写入**。新加的 `cost.k-max`
硬顶规则要重启 DSH 才会生效，在此之前跑基准，相关任务必然失败。

这件事本身不严重，但它会伪装成"决策有 bug"——第一次看到
`期望 deny → 实际 deny (no-authorization)` 时，很容易以为是判定逻辑错了。

所以 `run-cbs.mts` 里加了**环境自检**段：先把基准集依赖的规则/授权
在当前库里查一遍，缺哪些、影响哪几条任务，在成绩之前先列出来。
**把"环境没同步"和"代码有问题"分开，能省下大量无意义的排查。**

### 11.3 发现二：PII 冻结规则是一条从未生效过的死规则

这是首跑最有价值的产出。

- 冻结规则写的是 `person-brain:learn.policy.pii-redaction`（**带后缀**）
- 业务侧实际传的是 `person-brain:learn`（**裸 scope**）
- `getFrozenRule()` 是 `WHERE id = ?` **精确匹配**

→ 这条 PII 冻结规则**一次都没有被命中过**。基座以为自己有 PII 保护，实际上没有。

修法有两条：在 `decidePure()` 加 payload 级 PII 扫描（治本），
或把冻结规则改成前缀匹配（治标，且会让 scope 命名空间变得含糊）。

**这里刻意不修。** CBS 的价值就在于暴露缺口；如果顺手把缺口填上，
就变成了"为了让分数好看而改代码"——正是这套系统要防范的奖励黑客。
宁可让 C(t) 带着真实的 0.725 起步。

### 11.4 一个意外收获：A3 破产的真实实例

设计文档第 8 节列过 A3（可判定性）破产的三种情况，第三种是
**"提议空间不含解"**。PII 缺口就是它的第一个真实实例：

- 缺口客观存在，CBS 能稳定测出来（可判定 ✓）
- 但修复它需要**代码级改动**（payload 扫描），
- 而 evolve 的提议空间只有 8 种 kind（加规则/加技能/改提示/…），
- **没有任何一种能表达"改 decidePure 的实现"**

→ 这个缺口会永远停在 0 分，除非人来改代码。

这恰恰证明了第 8 节的价值：**A3 不能保证系统能修好所有问题，
只能保证它能准确知道哪里有问题。** 把这两件事混为一谈，
是很多自进化系统翻车的根因。

### 11.5 写代码时踩的两个坑

**坑一：中文路径被百分号编码。**

```ts
// 错
new URL('../../diechi-home/', import.meta.url).pathname
// → D:/%E6%A1%8C%E9%9D%A2/.../diechi-home/
```

`SupervisorDb.open()` 自带 `mkdirSync`，拿到编码路径会欢快地
在 D: 盘下建出一棵名为 `%E6%A1%8C%E9%9D%A2` 的乱码目录树，
然后在一个全新的空库上跑出一份「冻结 0 条、授权 0 条」的假报表。
第一次看到 liveness 0/16 时差点以为决策逻辑崩了。

正确写法是 `fileURLToPath(new URL(...))`，**且存在性检查必须在 open 之前**
——等它把目录建出来再检查就晚了。

**坑二：把 reason 算进判定，会把"改进"判成"退步"。**

最初的实现是"期望 reason 给了就一起比"。结果给 `shell:exec`
加一条冻结规则后，它的拦截理由从 `no-authorization` 变成 `rule-frozen`，
**安全目标达成得更好了，分数却掉了**——等于惩罚系统把隐式保护升级为显式保护。

修法：加 `strictReason` 标记，默认只比决策不比理由；
只有那些**测的就是理由本身**的任务（验证冻结规则存在、验证护栏触发）才严格比对。
