## 0. 一句话背景

三架构 = 被升级者（DSH）+ 升级设计者（diechi-evolve）+ 监督者（diechi-supervisor）。
此前两个致命缺口：① DSH 进程一死三架构全灭（同进程插件）；② 三架构插件**从未被
cordis 真正加载过**（三个包的 `cordis.yml` 都是 `[]`）。本条线的工作就是把这两个洞补上，
并跑通「崩溃自愈 + 信号驱动升级 + 坏补丁降级」三条端到端链路。

## 2. 验证结果（全部真实系统实测，非 mock）

| 场景 | 结果 |
| --- | --- |
| 崩溃自愈 | SIGKILL 3090 → watchdog 2–6s 拉起新 PID，HTTP 200，负样本按次累积 ✅ |
| 信号驱动升级 | supervisor 真实 execute 写信号 → 6s 内被消费 → 杀→换补丁→拉起，目标文件 sha `70285f13`→`e19a0f50` ✅ |
| 坏补丁降级 | 补丁目录不存在 → 跳过补丁 → **仍拉起**，只试一次不无限重试 ✅ |
| 基座保护 | `callerToken:'diechi-evolve'` 调信号工具 → 返回 `callerToken 必须为 "human"` ✅ |

**设计要点**：计划内升级刻意**不记负样本**（human 授权动作若记成 deny，evolve 会误当
崩溃聚类）。不是 bug，`tests/basic.spec.ts:141` 有断言。

## 4. 信号升级端到端怎么复测

1. 停正式 watchdog，起测试实例：`WATCHDOG_INTERVAL_SEC=5 node --import tsx packages/host/diechi-process-watchdog/src/cli.ts`（后台）
2. 通过 supervisor 真实执行体写信号（勿手搓 JSON）：收集 supervisor tools 的 mock ctx 后调真 `execute`，只依赖 `process.env.DSH_HOME` 与文件系统
3. 等 watchdog 下一轮：杀旧 DSH → 应用补丁 → 拉起
4. 验证：`history.jsonl` 新增 `signal-consumed`；新进程加载补丁版文件；负样本数不变

## 5. 环境坑（本机实测踩遍，务必先读）

1. **pnpm 完全不可用**（安全钩子拦 `_tmp_*`）→ 装依赖用 PowerShell `New-Item -ItemType Junction` 做目录联接；跑工具直接 `node node_modules/<pkg>/<bin>`
2. **vitest 4 worker OOM** → 改 `node --import tsx --test`
3. **cordis.yml 新增插件必须用 `- insert:`**；裸 `- id:` 语义是「修改已存在 entry」，新增会报 `entry not found` 并**静默跳过**
4. **bundle 的 `cordis.yml` 为 `[]` = 不加载任何插件**；写进 profile 的 `bundles` 只决定 patch 应用顺序
5. **中文路径**：`isDirectRun` 必须用 `pathToFileURL`；bash 传 `DSH_HOME` 用正斜杠可行
6. **构建前必须停 3090**，否则 rolldown 写 `lib/index.js` 报「拒绝访问」；别跑全量 tsdown（重写 226 个包），用临时单包配置
7. `wmic`/`tasklist` 被禁；`netstat`、`taskkill`、`node` 可用；PowerShell stdout 常为空，结果写文件再读
